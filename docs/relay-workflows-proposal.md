## Goal and agreed constraints

Turn Relay into a company assistant that uses uploaded evidence, splits a request into dependent and independent steps, asks the appropriate teammate for approval, and then performs the permitted work automatically. Keep the product focused on the Graph Hacks tracks, with FalkorDB central to company knowledge, routing, execution history, and memory.

The user explicitly requested that the existing app be pushed first, that a feature plan be presented for approval, and that new implementation begin only after approval. A remote check on 2026-10-17 confirmed that local HEAD and GitHub branch `work` both point to `c40a08f3bdb9cb5a55be26f2a83852840e03dc7f`; the checkout was clean before this proposal was added. No app push was needed.

Success means one convincing end-to-end workflow with real outputs, visible evidence, an authenticated human decision, and restart recovery. It does not mean a large catalog of disconnected features or a guarantee of a hackathon prize.

## Recommendation and alternatives

1. **Recommended: a focused approval-and-execution workflow.** Extend the existing company graph, assistant, memory, and actions into a complete document-to-result experience. This directly answers the user's request and gives all three tracks concrete proof.
2. Add attachments and keep task approval as a status change. Smaller, but does not demonstrate work being performed or meaningful agent coordination.
3. Build a general workflow designer with many external integrations. Broader, but increases setup, failure modes, and demo complexity. Defer it until the focused workflow is reliable.

The first release remains one company workspace. It adds real member identities and department permissions without attempting a multi-tenant enterprise platform.

## Proposed feature set

### 1. Attachments that become usable company evidence

- Accept selectable-text PDF, TXT, Markdown, and a narrowly defined CSV format. Initial limits: five files per request, 10 MiB per file, 50 PDF pages, 200,000 extracted text characters per file, and 2,000 CSV rows. Reject unsupported, encrypted, empty, or oversized documents with a clear explanation.
- Supply invoice and purchase-order CSV templates with exact columns `item_id`, `quantity`, `unit_price`, and `currency`. Limit columns and cell length; reject ambiguous duplicate item IDs and malformed numeric values. No currency conversion.
- Record uploader, department, access classification, original filename, content hash, version, and processing status. Store blobs outside the public static directory, using generated storage IDs.
- Let the user attach selected sources directly to a question. Retrieval must explicitly include relevant chunks from those sources instead of relying on the existing global 20-source limit.
- Answers open the precise supporting PDF page, text paragraph, or CSV row. Preserve original excerpts and use readable, deduplicated citations.
- Suggest typed graph links to existing projects, suppliers, people, and teams, with a compact confirmation step during ingestion. Unknown or conflicting links remain unresolved; extraction cannot silently replace company facts. Every accepted relationship retains evidence provenance. A general graph editor is outside scope.
- Finance-classified uploads stay out of agent retrieval, semantic extraction, and model context until a valid approval permits processing. Classify and route from uploader-supplied metadata and company policy, without reading protected content first. Minimal transport/type validation is allowed before approval.
- Upload hashing and the authorized auditor's own source viewing are permitted before approval. Agent parsing, retrieval, and model inspection are not. A grant is specific to the named run; it never globally unlocks the attachment for unrelated chat or future investigations.

### 2. Visible workflows with independent branches

- Add a run view showing steps, prerequisites, owners, cited inputs, progress, and outputs. A readable list accompanies the graph.
- Support a bounded plan made from implemented tools, not arbitrary code generated by the model. Reject unsupported operations and cyclic dependencies.
- Implement one invoice-review template first: company-context branch, gated finance-comparison branch, and a joined report/case step. The model may select relevant allowed inputs and explain the plan; it cannot invent new executable branches. Additional templates are later extensions.
- Independent steps may execute concurrently. For example, a company dependency check can finish while the finance branch waits for its reviewer; joined results wait for their prerequisites.
- Use clear states: queued, running, waiting for approval, completed, failed, rejected, cancelled, and stale. Poll persisted progress initially; a separate queue service is unnecessary for the first version.
- Cancellation stops new steps and preserves the record of work already performed. Failed steps offer retry without repeating completed effects.

### 3. Department approvals with minimal human effort

- Introduce server-authenticated workspace members, initially an operator/requester and a Finance auditor, with administrator-controlled role assignment. Provision accounts securely, hash passwords, and use protected sessions. A client-side role selector must never grant authority.
- Keep requests in a real **Approvals inbox inside Relay**. The assigned reviewer sees the requester, exact file versions, permitted tools, planned outputs, output audience, and the reason their approval is required.
- The default finance policy requires approval before agent inspection of protected finance content. Company-level policy is enforced by the server and cannot be disabled by a requester or by an attachment instruction.
- Offer two run preferences within that policy: **Review each change** and **Auto-run permitted steps**. The latter performs allowed work automatically while still stopping at mandatory department gates.
- **Approve once** authorizes only the displayed bounded workflow and input versions. It can cover reading the selected finance files, comparing them, producing the report, and creating the stated internal follow-up. It is not unlimited permission for future tasks.
- **Reject** stops the protected branch. **Request changes** records a reason and creates a revised proposal. Missing reviewers or expired approvals leave the branch waiting; elapsed time never counts as consent.
- Apply access checks to every route: attachments, search, graph data, source details, chat retrieval, memory, workflow results, and downloads. Derived artifacts inherit restrictions; the approval explicitly identifies whether the requester may view the resulting report.
- No Slack or email delivery is included in this phase. A teammate receives and handles the request in Relay.

### 4. Execute useful work and show the result

The first tool workflow is **reviewing an Atlas launch supplier invoice against its purchase order** and explaining the company impact.

The server-controlled tool set will:

1. Follow FalkorDB relationships from the supplier/service to the project, owner, and reviewer.
2. Compare the selected invoice and purchase-order CSVs using decimal arithmetic, reporting missing/extra lines and quantity/price differences with row references. Same-currency totals are calculated by code, not by the language model.
3. Save a reconciliation result and a downloadable HTML report plus CSV discrepancy table.
4. Create an assigned internal exception case when discrepancies exist, linking its evidence and affected company entities. A matching invoice produces a completed comparison report without an invented exception.
5. Save the decision, tool executions, report, and follow-up links as company memory.

An invoice mismatch establishes a finance exception, not automatically a launch blocker. Claim a readiness block only when an explicit company policy/source and directed dependencies support it; otherwise show the connected project and owner and explain the uncertainty. Preserve the existing `DEPENDS_ON` direction from dependent to prerequisite, even when the UI presents impact in the reverse direction.

Execution means actual stored artifacts and cases, not merely changing an action label to complete. An execution receipt records the tool, input versions, approver, time, result, and output links. Groq explains supported results and proposes bounded steps; the server validates permissions, source references, and tool arguments.

This workflow does not pay an invoice, move money, send an external message, or change production systems. A future external connector can add a separate concrete capability after the core workflow is proven.

### 5. Resume, remember, and explain what changed

- Persist workflow and branch state, decisions, input versions, receipts, outputs, and relevant memory. A refresh or executor restart must not lose a pending review or duplicate a completed result.
- Link later questions to previous runs: for example, "What did Finance approve, what did Relay find, and who owns the next step?" Previous approval is historical evidence, never blanket authorization for a new run.
- Add a decision timeline showing evidence -> proposed plan -> approval -> execution -> result. Include the reviewer identity and the exact permission granted.
- **Signature demo moment:** replacing an attachment creates a new version. Graph dependencies identify which steps and outputs depend on it. Those results are marked stale and their approval is invalidated; unaffected completed branches remain reusable. Reapproval runs the affected branch and downstream report only.
- Previously created artifacts and decisions remain visible as historical versions. Invalidation never pretends to undo an already executed action. Update the linked exception case through a new receipt instead of silently duplicating it.

### 6. Polish the existing experience

- Clear corrected source-form validation errors.
- Replace repeated raw source IDs with readable evidence references.
- Give the answer/workflow panel more reading space and provide clear pending, empty, error, and recovery states.
- Retain accessible keyboard operation and small-screen support.
- Keep Live model and Guided demo visibly distinct. Show the completed new workflow with live Groq during submission recording; provider failures remain visible instead of becoming fake successes.

## Architecture and data ownership

Reuse FastAPI, React/TypeScript, React Flow, FalkorDB, LangGraph, and the existing Groq-compatible client. Add lightweight PDF parsing and standard-library CSV parsing; do not make heavy optional ingestion frameworks a prerequisite.

FalkorDB owns company entities, source/chunk metadata, ownership and department policies, workflow/step records, approvals, execution receipts, artifacts, and searchable memory. Use typed relationships such as `DEPENDS_ON`, `USES_SOURCE`, `ASSIGNED_TO`, `REQUIRES_APPROVAL`, `APPROVED_BY`, and `PRODUCED`. Reads, routing, impact analysis, and invalidation must query this graph rather than using it only for visualization.

LangGraph coordinates supported tools, conditional branches, and approval interruption/resumption. SQLite retains engine checkpoints; it is not the primary company database. Approval validity and execution eligibility are always checked against the authoritative graph state when a step resumes.

Start with one background executor and atomic step claims. Use stable run/step/version keys and idempotent artifact/case writes so double approval, retry, and crash recovery return the same logical result. Reconcile an interrupted running step from its receipt before rerunning it. Add bounded concurrency and provider retry limits; do not claim unrestricted scale or general exactly-once external execution.

Treat uploaded content as untrusted evidence, never permission or an instruction to execute a tool. Restrict relation names and tools to validated allowlists, parameterize database queries, and escape content in viewers and generated HTML reports.

Keep the existing investigation, Ripple, Knowledge, and Memory flows working. Extend graph types and migrate existing actions explicitly; old manually completed actions must not be relabeled as newly executed workflows.

## Deployment and cost boundary

The current Render free service has temporary storage. It cannot support a promise that uploads, approvals, or memory survive service replacement or redeployment.

Include a deployment configuration for durable storage covering FalkorDB data, uploaded files/artifacts, and workflow checkpoints. For the first single-instance deployment, a persistent disk is the simplest option to evaluate; use a separate durable database only if required by the hosting constraints. Validate recovery with the chosen storage, document backup/restore, and avoid promoting sensitive real-company usage before that setup is verified.

Feature approval permits development and configuration preparation. It does not authorize buying a hosting plan or consuming a new paid service. Present the actual Render instance/disk cost before activating a paid configuration. Existing credits are not proof that a specific plan is active or sufficient.

## Implementation sequence after approval

1. **Identity and durable state:** member sessions, department access, graph schema/versioning, migration, and storage configuration. Preserve the current demo while adding the new boundaries.
2. **Evidence pipeline:** upload validation, bounded parsing, protected file access, source chunks, explicit attachment Q&A, and evidence viewers.
3. **Workflow engine:** typed plans, independent branches, graph-routed approval inbox, pause/resume, rejection, atomic claims, and restart recovery.
4. **Real execution:** CSV comparison, reports/downloads, internal exception cases, receipts, and graph-linked result memory.
5. **Change-aware replay and polish:** version invalidation, reusable unaffected branches, decision timeline, citation/form improvements, and a live-model demo.
6. **Verification and delivery:** test the full flow, commit/push the approved implementation to the user's repository, document deployment settings, and verify the running deployment when hosting access and configuration permit it.

## Acceptance checks

- A new uploaded document answers a relevant question with the correct file and page/row citation; unsupported answers explicitly identify missing evidence.
- Before approval, the finance branch performs zero protected content reads or model calls containing that content. Direct source, search, graph, memory, report, and download routes do not bypass access checks.
- An unauthorized member cannot approve a finance request, spoof reviewer identity, or change policy. Session and cross-site request protections are exercised.
- The independent company-context branch completes while finance waits. Correct approval resumes the allowed branch and produces the joined result without another manual run click.
- Rejection, cancellation, missing reviewer, and approval expiry prevent unauthorized execution and preserve an understandable history.
- The known invoice fixture produces the expected decimal totals, discrepancy rows, report, and owner-assigned exception case. A matching fixture creates no false discrepancy.
- A financial discrepancy without an explicit launch-gating policy is never labeled a proven launch blocker. An approval for one run cannot authorize an unrelated question or another file version.
- Repeated approval, simultaneous resume requests, provider timeout, and restart at each execution boundary do not duplicate reports or internal cases.
- Updating one attachment invalidates only dependent approvals/results, preserves unaffected results, and requires valid new approval before the changed finance work executes.
- Malformed CSV/PDF, duplicate row identifiers, oversized files, injection-like attachment text, and unsupported formats fail clearly without granting tools or leaking content.
- New memory answers refer to stored decisions and outcomes while respecting their access scope. Stale outputs are visibly marked.
- Real database integration tests, API/authorization checks, frontend typecheck/build, and browser flows cover the changed behavior. Desktop, narrow viewport, keyboard, and approval/error states are checked.
- Persistence across service replacement/redeploy is claimed only after testing the configured durable deployment. Groq live behavior is claimed only after a real provider-backed test.
